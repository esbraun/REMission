## 2. Authority and minimal versioned interfaces

New service types use `schema_version="1.0.0"`, `contract="LIVE-HOLD-01"`, `synthetic=true`, strict unknown-field rejection, existing Identifier/Sha256/VersionRef and aware timestamps. They are service command/receipt records, not new observed kinds or amendments to v1/v2 Record. Canonical digest uses the existing service canonical encoder; raw archive byte hashes remain raw. No secret/session cookie enters payloads, exports or audit. Auth-generation digest may be retained only in protected service audit as already used by foundation.

### Server configuration

Add an immutable, versioned `LiveHoldAuthority` registry selected by host configuration, with its digest persisted in each admitted operation:

- `authority_id`, VersionRef, enabled state; exact OBS-REP binding and accepted archive verifier/configuration identity; qualified producer/run/source-registry identities. An ordinary `TrustedExportAuthority` verifies the archive but is insufficient for live projection.
- Explicit grants keyed by `(account_id, service_patient_id, source_id, source_version, run_id, partition_id)`, with allowed operation `invalidate`, exact archive-patient identity, synthetic ownership-evidence ref, approved trigger-rule refs, authorized episode namespace, follow-up owner/account and escalation destination. Owner must equal current `patients.owner_id`; the authenticated principal must equal that owner in this first single-doctor service. No source-only service credential or extra nurse/research role is introduced. A future service-principal adapter requires another reviewed contract.
- Exact accepted source package/manifest digest and archive ID, with its configured root and authority, never a caller path. A grant may cover a listed series of exact package revisions, not arbitrary files sharing a source label. Persist which package revision supplied every dependency. Every reference resolves within the same run/partition/patient/episode where that type carries episode identity.
- For each permitted trigger rule: required review definition VersionRefs, responsible doctor role, configured follow-up task policy VersionRef. This policy explicitly supplies a synthetic due-time rule or exact due time per package and escalation destination; no implicit clinical urgency/default interval. Imported follow-up refs must match configured responsibility; an overdue imported due date remains overdue, not silently advanced.
- Optional explicit `ManualReviewRule` bindings described in section 6. Absence disables clearance for that episode, not invalidation. No wildcard fallback, numeric threshold or elapsed-time clearance.

Configuration is administratively installed, never mutable by an ordinary HTTP request. Every process is bound to the same persisted active authority/capability generation under the gate as specified below; a merely local registry digest is insufficient. Missing/revoked grants deny new operations, including retries until current authorization is valid. Removing a rule never clears an episode. No ownership-transfer endpoint is introduced; a future migration must preserve/reassign open obligations explicitly or remain blocked.

### 2A. Common capability and authority generation; no mixed deployment

Required initial runtime is the pinned Linux service container on one local SQLite volume and its shared lock file. Native Windows is not enabled for this package without separate equivalent OS-lock/cutover qualification. All API, CLI seed/reset/replay, migration, export and maintenance processes that can touch current authority are participants. Read-only immutable research copies are not current authority.

Add one authoritative `service_control` row containing `database_instance_id` (new UUID), `capability=LIVE-HOLD-01/1.0.0`, `minimum_reader_writer_capability`, monotonic `authority_generation`, exact `authority_sha256`, exact `review_rules_sha256`, `enabled`, `activation_id`, `activated_at`, and monotonic last committed receipt time. Every participating process is launched with the exact instance ID, capability version and a read-only authority/rules bundle. On startup, before migrations or serving any route, compare these values to the DB; never create an old Store instance that runs legacy startup SQL first. Under the common gate, before **every current read or mutation**, re-read the control row in the admission transaction and compare all bound fields/digests, not just local content. Mismatch returns503 `service_generation_mismatch` with no current projection, write, receipt alias or cached success. This check also covers CLI/reset/replay and internal function entrypoints. A supported service process cannot silently downgrade to archive-only when current authority is unavailable. Immutable historical reads may remain read-only but must not claim current status.

There is no HTTP registry update or rolling mixed-capability upgrade. Missing service_control is allowed only by an explicit offline migration command under the quiescence/new-volume procedure below; ordinary server/CLI startup refuses it and cannot implicitly bootstrap authority. Initial ec18 cutover is mandatory because ec18 cannot enforce the new row or gate:

1. Stop routing current requests, drain in-flight requests, then stop **all** old API/CLI/replay/administrative processes. Record supervisor/container process inventory and verify no live writer/DB handle remains; inability to establish quiescence blocks deployment. Disable their restart policies and old command launch configuration.
2. Preserve original DB/WAL state by a consistent SQLite backup after quiescence. Leave this historical copy offline/read-only. Restore into a **new deployment-private volume/path** with a new database_instance_id and new shared lock file. Only the explicitly qualified new runtime receives this volume; old runtime mounts/configuration cannot reference it. Remove the old API routing/ports from the current service identity. Old image restart must fail to mount/access the new authority volume; an old offline copy cannot be advertised as current.
3. Under the exclusive gate on the new volume, apply the integration-owned migration, populate control row and exact configured registry/rules, initialize patient safety journals, validate immutable old hashes and unchanged patient/approval/history data, and record an activation receipt. On failure keep new volume unrouted; do not partially enable. The old service is not silently resumed as current after any new live operation.
4. Start only new-capability processes with matching digests/instance ID; each self-checks before exposing readiness. Verify all participating process inventory, mounts, config/capability digests and health. Route current requests only after those checks. Readiness must distinguish capability mismatch from ordinary health. A privileged operator bypassing mount restrictions is outside deployment assumptions; an ordinary stale worker is specifically prevented, not dismissed as a privileged DB writer.

Later authority/rule/enablement changes also use full drain/stop and gate-held administrative transaction; no mixed registry hot reload. Increment authority_generation even if payload bytes revert to an older version. Persist exact new registry/rule digests and a cutover audit. Never delete latches, obligations or original rules. For every patient with an open episode, advance patient/state/eligibility once (consent unchanged), append `authority_changed` operation, create a held/stale decision, invalidate drafts and all reviews from earlier authority generation. No source grant/rule removal closes any obligation. Retain the union of unresolved required obligations; removal of a definition leaves it explicitly unsupported rather than removing the requirement. New or stronger obligations are added. Relaxing/substituting an existing obligation requires a separately reviewed policy change; it cannot happen via this generic cutover command. Absent rule anywhere in the episode blocks its whole clearance.

Every live receipt/review/projection records the active generation and digests. Invalidation/core state admission rechecks control row after writer wait. Clearance requires review.authority_generation=current generation **and** current registry/rule digests and all active obligations; restarting an old G1 process after G2 cutover fails under gate, even if it retained its old config. A supported process sees mismatch before idempotent result lookup as well; an old receipt remains retrievable by a currently authorized process. Changing an enabled flag never disables latch enforcement: it may deny new integrations, but current reads/mutations still enforce persisted latches. Unknown/newer capability refuses startup; no backwards auto-migration.

Clock regression below the last committed receipt/cutover time fails current mutation with `service_clock_regression`; do not fabricate an advanced clinical timestamp. Equal server timestamps are allowed and ordered by operation sequence. This makes patient journal visible prefixes well-defined without inferring causality from wall-clock equality.

Mandatory deterministic deployment cases, in addition to LH03–05/17/19: two qualified processes A/G1 and B/G2, stop/cutover then intentionally attempt A restart/operation with G1 →503/no mutation or clearance; grant revocation and changed required definition reject the old request/review even with unchanged payload. Attempt ec18 stale API/CLI process against new volume → mount/access denied and no current route; inventory must prove no old worker remains serving the old volume as current. Kill cutover before transaction commit → old generation intact and new routing off; kill aftercommit before start → new generation/held versions recover, stale workers still denied. Test config enabling/disabling, rollback-to-old-bytes with new generation, simultaneous startup and a held multi-episode patient. These are planned acceptance schedules, not executed results.

## 3. Receipt time, serialization and atomicity

**Proposed runtime boundary:** one SQLite database on a local filesystem, all cooperating service/replay processes sharing one canonical DB identity and one process-shared exclusive admission gate. Use a persistent sidecar lock file at `<resolved database path>.admission.lock`, deployment-created within the DB trust boundary. Never delete/replace it during operation. Combine an in-process mutex with a real OS interprocess lock (POSIX `flock` in qualified Linux containers; Windows byte-range lock with dedicated byte/held handle if Windows service execution is supported). Unsupported filesystem/lock capability fails startup. No NFS/shared-host distributed operation is claimed. Processes mounting the DB mount the same lock inode/path; private per-container lock copies are forbidden. Test separate processes, not only threads. Platform implementation/dependency choice remains Sol's bounded library/runtime responsibility, with independent verification before enabling the route.

The global gate is deliberately coarser than per-patient locking: avoids multi-patient archive deadlocks and matches SQLite's single writer. Order: **gate → DB connection/autocommit read authorization → BEGIN IMMEDIATE → final checks/writes → COMMIT/ROLLBACK → close DB → release gate**. Finish any initial read transaction before BEGIN IMMEDIATE; never upgrade a held read snapshot or wait for gate while holding a DB transaction. Expensive immutable archive verification may precede gate, but compare bytes/configuration digests again inside; stale ownership/auth/lineage/versions fail inside. Recheck authentication after any writer wait. Every relevant service write, replay/archive entrypoint, current-workspace/panel/permission read and draft validation participates. Login/session/credential/configuration mutation also uses this order so authority cannot change behind receipt. History/raw immutable reads need not wait; current authority never derives from them. Nested trusted helpers receive transaction/gate context; no reacquisition/competing transaction. Direct operational DB modification outside this contract is unsupported.

Network body arrival is transport observation only. **R is sampled under the gate after successful initial authentication, owner/source/evidence validation**, before waiting for SQLite writer. A valid operation retains gate through final validation and commit. Thus an authenticated hold with R waiting for DB writer prevents later approval entering its transaction or observing ready current permissions. Current reads wait or return `503 safety_admission_busy` with no ready projection; approval times out likewise without writes. No success receipt while pending. This resolves LH13 without calling HTTP arrival durable acceptance or claiming an in-memory lock survives a crash. Pre-existing approval already owning gate can finish first; later hold invalidates it. Wall-clock equality never overrides serialized operation order.

If process dies before commit, OS lock release and SQLite rollback leave **no accepted live receipt/latch/cursor**; retry required. R from an uncommitted attempt is not retrospectively durable. Aftercommit death recovers durable latch/receipt/cursor before current reads; retry returns original R. This is rollback versus response loss, not a promise of durable network delivery. Client retains key while outcome unknown. Do not create a separate successful “received” transaction before latch transaction. A future durable inbox/async mechanism requires another reviewed two-phase contract.

Transport-arrival diagnostics, if captured, are not clinical receipt/source availability. Preserve source event/recorded/available A in archive. Mandatory supplementary `LIVE-SAFETY-EXPORT / 1.0.0`, fully specified in section 3A, carries service operational facts separately from the unchanged observed projection. Do not add a member to ObservedHistory/LearnerHistory v1/v2 or infer that their current readers accept it. Current safety folds committed operations inclusively at R; the supplementary learner product filters strictly before K. At K=R a pending current read yields busy, never ready; after commit safety is held while the new live fact remains absent at strict K=R. Archive reconstruction retains original A; a fact visible in an archive before R does not prove live-service receipt. Operational facts are neither symptoms nor extra likelihood observations.

### Patient journal, strict prefix and operation fold

Maintain a per-patient gapless `patient_sequence` starting1 in the immutable service journal, separate from the DB-wide committed-operation cursor used in live receipts. Each fact has `schema_version`, `kind=live_hold_fact`, synthetic flag, patient/journal/operation IDs, patient_sequence, previous fact SHA256 (null only sequence1), operation type, episode ID/generation where applicable, authority generation/config/rule digests, `event_at`, `recorded_at=R`, `available_at=R`, and typed operation payload. Hash covers the full canonical fact excluding only its own computed hash; the file need not embed that computed hash because successor/manifest bind it. No owner account/auth token/free-text clinical narrative/private source is exported. Safe reason codes, exact public observed evidence refs and requirement VersionRefs are permitted. References from a visible fact may name previously archived facts, but never include their unavailable payloads automatically.

Operation types and payloads are closed:

| Type | Required payload and fold |
|---|---|
| `baseline` | Exactly sequence1, recorded at initial activation, empty independent episode set on first ec18 migration and explicit scope independent_live_holds. On migration from an already capable version, preserve the original journal/baseline, never reset it. Baseline does not claim absence of ordinary intercurrent or generic clinical holds. |
| `invalidate` | Episode identity/generation, `action=open|strengthen`, exact accepted trigger refs, complete resulting active trigger set/digest, safe reason codes, complete obligation IDs/definition refs/digest, original source event E<=R. Open requires new episode or next generation of a closed episode; strengthen requires same active generation and monotonic trigger/obligation union. Makes/keeps that episode held. |
| `review_recorded` | Episode/generation, exact live review ID/hash, current_review_at, reviewed trigger/obligation digests, rule refs and authority generation, result=pending|satisfied. Must target active generation; does not change held state. Satisfied means all active obligations under configured rules, not selected subset. |
| `clearance` | Active episode/generation, exact prior live review ref, trigger/obligation digests, rule refs and authority generation; requires prior visible satisfied matching review, same generation/facts/config, no intervening invalidation/dispute/authority change. Closes only this generation. event_at=R, never imported source resolution time. Does not assert ordinary treatment eligibility or authorize a draw. |
| `authority_changed` | Old/new authority generations/digests, per-active-episode resulting obligation sets/digests (only retain/add), prior journal identity. Invalidates prior review usability, retains every active latch. No episode with absent rule becomes clearable through this operation. |
| `evidence_disputed` | Exact affected observed refs and episode/generation, reason=corrected|retracted|superseded|unresolved. Invalidates dependent review usability, retains latch and obligation set. Does not remove trigger or resolve episode. |

Other current clinical mutations still invalidate reviews through versions; they do not fabricate an independent hold. To make the consumer review fold equally conservative, when such a mutation stales an active review, append `evidence_disputed` with reason=`current_context_changed`, affected episode/generation and changed context digest (empty record-ref list allowed only for this reason). This is journal metadata, not a second patient version increment beyond the originating mutation. Transport-key aliases, rejected operations and retries produce no journal fact. `event_at=R` for baseline/review/authority/dispute; source E only for invalidation. No removal/tombstone rewrites this service journal. Archive corrections remain in their existing separate lineage; their effects on live review are explicit non-clearing journal facts.

Server R is nondecreasing per common control row; equal R facts order by patient_sequence. At export K, select facts with event_at<=K and recorded_at<K and available_at<K **before folding**. Since event<=R and R is nondecreasing, visible facts form a prefix starting1; gaps, swapped entries, duplicate sequence, wrong predecessor/hash or future/equal-K fact reject. A batch with equal R is wholly visible only when K>R. The trusted exporter/authority proves prefix completeness against the committed journal; a self-consistent shorter prefix is insufficient. `through_patient_sequence` and count refer only to the visible prefix, never disclose later operations/counts. Prefix head is the SHA256 of the last canonical fact; empty prefix uses SHA256 of empty bytes. K before/equal baseline availability yields empty prefix, uninitialized/unknown, null baseline and no “not held” conclusion. After a visible baseline and complete verified prefix, not_held means no independent live episode remains; it is never global readiness. No omitted baseline/default empty list is allowed to mean safety.

Export snapshot is read under common gate after active-generation check and one committed DB read snapshot, binding observed projection and journal prefix to the same patient/K. Refuse future K>S. Snapshot ID/digest binds service instance, K, observed artifact, prefix head and generation, excluding the subsequent publication receipt; any corrected context yields a different export ID. Historical exports are immutable and cannot authorize current commands. Physical current workspace uses inclusive persisted latch at the current transaction, **not** the strict K export fold to decide approval. A hash-qualified complete prefix at an old K cannot override current service safety.
