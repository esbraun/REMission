# G0 ledger conventions and critique handoff

The [JSON ledger](g0-task-test-ledger-20261020.json) is a planning coverage index, not an executed test report. [Technical decomposition](g0-technical-plan-20261020.md) supplies package boundaries and acceptance. Canonical prose wins over excerpts. Every legacy atomic unit is retained conservatively, including explanatory headings and table headers: a mapped test obligation is not a claim that every prose fragment needs a redundant automated test.

Each coverage row has its own stable test ID and joins one or more packages. Package defaults are explicit in `task_defaults`; each task overrides them where applicable. Reviewers must resolve those defaults when reading a task. `methods_profile` joins the concrete protocol/estimand/DGP/truth/allowed-information/source/failure profile; nonmethods tasks use explicit `N/A`. Proposed task owners are roles, not invented assigned threads. Unassigned worktree/branch/reviewer/candidate fields are null and block dispatch or review as appropriate. The accepted specification base is a reference, not a promise that future branches remain on that base after integration.

`expected_acceptance` copies a canonical scenario/test expectation or names the exact canonical atomic unit plus its task's observed acceptance. It is an obligation to turn the canonical unit into a meaningful seam/integration/statistical/manual check before its gate. Test IDs do not assert that test source files exist. G0-CONTRACT must refine per-unit checks where a package-level check is insufficient; it may consolidate coherent checks while preserving every row and all expected outcomes. No coverage percentage replaces review of semantic completeness.

Invented planning identifiers are labeled by prefixes: `ASSIGN-` (ten assignment rows), `INV-` (thirteen software invariants), `DEMO-` (eight demonstration cases), `BROWSER-` (eleven integrated matrix rows), `HF-` (thirteen intended-user tasks). They supplement, not replace, canonical LEG/S/UX identifiers. The scenario manifest still needs explicit cell expansion and final version review under G0-DGP; the ledger's 32 family rows are not a claim of 32 total confirmation cells.
