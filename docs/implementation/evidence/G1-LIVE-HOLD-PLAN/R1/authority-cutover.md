### 2A. Common capability and authority generation; no mixed deployment

Required initial runtime is the pinned Linux service container on one local SQLite volume and its shared lock file. Native Windows is not enabled for this package without separate equivalent OS-lock/cutover qualification. All API, CLI seed/reset/replay, migration, export and maintenance processes that can touch current authority are participants. Read-only immutable research copies are not current authority.

Add one authoritative `service_control` row containing `database_instance_id` (new UUID), `capability=LIVE-HOLD-01/1.0.0`, `minimum_reader_writer_capability`, monotonic `authority_generation`, exact `authority_sha256`, exact `review_rules_sha256`, `enabled`, `activation_id`, `activated_at`, and monotonic last committed receipt time. Every participating process is launched with the exact instance ID, capability version and a read-only authority/rules bundle. On startup, before migrations or serving any route, compare these values to the DB; never create an old Store instance that runs legacy startup SQL first. Under the common gate, before **every current read or mutation**, re-read the control row in the admission transaction and compare all bound fields/digests, not just local content. Mismatch returns503 `service_generation_mismatch` with no current projection, write, receipt alias or cached success. This check also covers CLI/reset/replay and internal function entrypoints. A supported service process cannot silently downgrade to archive-only when current authority is unavailable. Immutable historical reads may remain read-only but must not claim current status.

There is no HTTP registry update or rolling mixed-capability upgrade. Missing service_control is allowed only by an explicit offline migration command under the quiescence/new-volume procedure below; ordinary server/CLI startup refuses it and cannot implicitly bootstrap authority. Initial ec18 cutover is mandatory because ec18 cannot enforce the new row or gate:

1. Stop routing current requests, drain in-flight requests, then stop **all** old API/CLI/replay/administrative processes. Record supervisor/container process inventory and verify no live writer/DB handle remains; inability to establish quiescence blocks deployment. Disable their restart policies and old command launch configuration.
2. Preserve original DB/WAL state by a consistent SQLite backup after quiescence. Leave this historical copy offline/read-only. Restore into a **new deployment-private volume/path** with a new database_instance_id and new shared lock file. Only the explicitly qualified new runtime receives this volume; old runtime mounts/configuration cannot reference it. Remove the old API routing/ports from the current service identity. Old image restart must fail to mount/access the new authority volume; an old offline copy cannot be advertised as current.
3. Under the exclusive gate on the new volume, apply the integration-owned migration, populate control row and exact configured registry/rules, initialize patient safety journals, validate immutable old hashes and unchanged patient/approval/history data, and record an activation receipt. On failure keep new volume unrouted; do not partially enable. The old service is not silently resumed as current after any new live operation.
4. Start only new-capability processes with matching digests/instance ID; each self-checks before exposing readiness. Verify all participating process inventory, mounts, config/capability digests and health. Route current requests only after those checks. Readiness must distinguish capability mismatch from ordinary health. A privileged operator bypassing mount restrictions is outside deployment assumptions; an ordinary stale worker is specifically prevented, not dismissed as a privileged DB writer.

Later authority/rule/enablement changes also use full drain/stop and gate-held administrative transaction; no mixed registry hot reload. Increment authority_generation even if payload bytes revert to an older version. Persist exact new registry/rule digests and a cutover audit. Never delete latches, obligations or original rules. For every patient with an open episode, advance patient/state/eligibility once (consent unchanged), append `authority_changed` operation, create a held/stale decision, invalidate drafts and all reviews from earlier authority generation. No source grant/rule removal closes any obligation. Retain the union of unresolved required obligations; removal of a definition leaves it explicitly unsupported rather than removing the requirement. New or stronger obligations are added. Relaxing/substituting an existing obligation requires a separately reviewed policy change; it cannot happen via this generic cutover command. Absent rule anywhere in the episode blocks its whole clearance.

Every live receipt/review/projection records the active generation and digests. Invalidation/core state admission rechecks control row after writer wait. Clearance requires review.authority_generation=current generation **and** current registry/rule digests and all active obligations; restarting an old G1 process after G2 cutover fails under gate, even if it retained its old config. A supported process sees mismatch before idempotent result lookup as well; an old receipt remains retrievable by a currently authorized process. Changing an enabled flag never disables latch enforcement: it may deny new integrations, but current reads/mutations still enforce persisted latches. Unknown/newer capability refuses startup; no backwards auto-migration.

Clock regression below the last committed receipt/cutover time fails current mutation with `service_clock_regression`; do not fabricate an advanced clinical timestamp. Equal server timestamps are allowed and ordered by operation sequence. This makes patient journal visible prefixes well-defined without inferring causality from wall-clock equality.

Mandatory deterministic deployment cases, in addition to LH03–05/17/19: two qualified processes A/G1 and B/G2, stop/cutover then intentionally attempt A restart/operation with G1 →503/no mutation or clearance; grant revocation and changed required definition reject the old request/review even with unchanged payload. Attempt ec18 stale API/CLI process against new volume → mount/access denied and no current route; inventory must prove no old worker remains serving the old volume as current. Kill cutover before transaction commit → old generation intact and new routing off; kill aftercommit before start → new generation/held versions recover, stale workers still denied. Test config enabling/disabling, rollback-to-old-bytes with new generation, simultaneous startup and a held multi-episode patient. These are planned acceptance schedules, not executed results.
