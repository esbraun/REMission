## Statistical evidence contract

Use [VAL-01–03](../spec/07-validation-protocol.md) and [RELEASE-01](../spec/08-gates-and-release.md#release-01--separate-evidence-statuses). A smoke run never satisfies recovery or SBC. ## Verification, prompt evaluation, and handoff

For the immediate cloud physician simulation milestone, use [CS-T1–T8](../implementation/poc-cloud-simulation-ledger-20261022.md#requirement-to-test-and-evidence-map). Handoff must identify the actual GCP project/resource, exact source revision/image and tested HTTPS origin; include deployed login rejection/success, session lifecycle/ownership, physician simulation and reload/container-restart/VM-reboot persistence evidence. Keep secrets out of evidence. Local tests and historical local browser runs cannot satisfy the cloud gate. Report later analytics/training and scientific validation separately as deferred or in their existing unfinished states.

Each task proposes checks that test its actual risk and acceptance contract. Apply [TEST-QUALITY](engineering-guidelines.md#test-quality--tests-that-detect-meaningful-failures), map all required UX/browser scenarios to checks, and verify actual auth middleware and persistence at integration boundaries. Small suites must preserve required behavior coverage; passing trivial tests or coverage thresholds is not acceptance. Do not require expensive MCMC for every CSS change, and do not treat UI screenshots as evidence of statistical calibration. Separate smoke plumbing, genuine saved-model demonstration, and repeated evaluation runs; the smoke preset is not evidence about borrowing performance.

Before marking a phase accepted, the orchestrator checks that all required tasks have owners, reviews, executed checks, versioned outputs, and no unacknowledged failures. Retain failures and abstention in the report. Model runs must record seeds, distinct observation IDs, priors/transport assumptions, data cutoff, fitting configuration, diagnostics, runtime, and output lineage. Evaluation summaries report Monte Carlo uncertainty and distinguish calibration under model-consistent simulations from robustness under misspecification.

Apply [worktree isolation and reviewed merges](delegation.md#worktree-isolation-and-reviewed-merges) to every package. Reviewers reproduce checks in their own worktrees pinned to the committed candidate and return reviewed head/base SHAs, findings, evidence, and an explicit ready-to-ship disposition. The orchestrator may open PRs and merge accepted branches into assigned integration targets without further confirmation only after independent review, passing required task/gate and repository checks, resolved findings, and accepted dependencies. Honor branch protections. Changed candidate or target base requires refreshed review and affected checks; Sol handles conflicts and repairs before Astra re-review. Record the PR and resulting merge commit, then delegate integrated verification. This engineering merge does not accept outstanding human/clinical gates.

Evaluate this prompt with a small representative suite before broad instruction changes: cold-start prior-only display; consent withdrawal; frozen support during a block/washout; a late upload excluded from an old snapshot; stale approval after a new hold; and sharp-null evaluation reporting. Measure completion against requirements, hard-constraint violations, unsupported claims, rework, latency, and reproducibility. Compare one targeted instruction change at a time across multiple runs; report observed tradeoffs instead of declaring a universally best prompt.

Before compaction, worker reassignment, or session end, persist the integration commit, plan revision, ledger status, worker/reviewer worktree paths and branches, candidate/reviewed head and base SHAs, PR and merge status, contract versions, artifact manifests, failed checks, pending workers, unresolved decisions, and exact next tasks. Preserve unfinished changes and needed artifacts before archiving worktrees. On resume, verify repository state, worktree ownership, and dependencies, read those records, and continue unfinished IDs. Do not overwrite accepted historical evidence or forget an outstanding human-review gate.

The release/documentation subagent must reproduce the demo from a clean checkout using the documented commands and pinned versions. The final implementation PR should explain the runnable behavior, include the requirement/gate report and verification evidence, and identify genuinely blocked reviews or computations. Do not call phase 6 complete without the plan's required real usability evidence, or call the synthetic app clinically validated.

For documentation revisions, include all changed specification, execution and evidence files. Application code and generated validation results belong to subsequent implementation work. The plan index and its canonical linked specifications govern requirements.
